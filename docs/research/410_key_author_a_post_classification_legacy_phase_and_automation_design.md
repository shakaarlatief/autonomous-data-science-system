## 2. Design principle: separate semantic questions before automating them

The later LEGACY work is not executed as one combined semantic pass.

Three distinct questions are kept separate:

    P6A
        CANDIDATE_GAP

    P6B
        FROZEN-HORIZON EVIDENCE SUBSTANTIATION

    P6C
        WITHIN-SOURCE GROUPING

This separation is deliberate.

Candidate-gap judgments must not be rewritten after repository evidence is observed.

Evidence substantiation must not be steered by the already-authored candidate-gap answer.

Grouping must not be steered by candidate-gap status, evidence results, source control roles, or prior grouping artifacts.

All three subphases remain the same logical Key Author A slot, but each semantic job is executed in a fresh process with a bounded input view.

## 5. P6A: candidate-gap authoring

P6A answers only:

    candidate_gap

The semantic source for each source packet contains:

    packet_source_id
    full unique source item catalog
    a mechanically derived list of item IDs eligible for candidate-gap judgment

Eligibility means the frozen P5 primary classification has:

    normative = true
    realization_required = true

The P6A author is not shown:

    normative_kind
    material
    source control role
    attention identities
    P6B evidence results
    P6C grouping results
    another key
    reviewer annotations

Items outside the eligible set receive:

    candidate_gap = false

mechanically at final assembly under the frozen addendum rule.

For every eligible item P6A authors exactly:

    item_id
    candidate_gap

P6A uses only the supplied legacy source material.

It does not receive repository evidence.

This preserves the reviewer-facing construct in which candidate gaps are identified from the supplied legacy material rather than post-hoc implementation evidence.

P6A output is frozen before P6B evidence for that component becomes available.

## 6. P6B: independent frozen-horizon evidence substantiation

P6B is a separate fresh semantic pass.

It receives the same eligible unique items but does not receive P6A candidate-gap values.

It also does not receive:

    material truth
    source control role
    grouping results
    witness/control identities

P6B receives read-only access to the exact frozen LEGACY evidence snapshot at:

    0a68787aee5f2c6332d6ee1fb6adbf0efe92a41d

The evidence snapshot remains outside writable key-author storage and is OS-enforced read-only.

P6B may inspect it only through bounded file-search/read capabilities.

No live repository, GitHub, web, MCP, network source, later commit, or writable repository is available.

For each eligible item P6B independently records one working disposition:

    REALIZED
    NOT_REALIZED
    NO_DECISIVE_EVIDENCE

and zero or more bounded evidence requests.

P6B does not alter candidate_gap.

A disagreement between frozen P6A candidate_gap and P6B evidence status is preserved as private evidence and never repaired by the task owner.

## 7. Evidence request and canonical evidence contract

P6B evidence requests are declarative.

The semantic author may identify:

    evidence_type
    fixed-snapshot relative path or bounded search scope
    locator_or_search_spec
    claimed frozen-horizon status

The semantic author does not author:

    revision
    match_count
    output_sha256

Those fields are resolved mechanically by the bounded control plane against the fixed evidence snapshot.

Canonical evidence refs use the frozen schema:

    evidence_type
    path
    revision
    locator_or_search_spec
    result

with:

    revision
        always 0a68787aee5f2c6332d6ee1fb6adbf0efe92a41d

    result.status
        REALIZED | NOT_REALIZED

    result.match_count
        integer | null

    result.output_sha256
        SHA-256 over the exact deterministic result bytes

Allowed evidence classes remain exactly those already frozen:

    exact path + revision
    exact test/validator evidence
    exact accepted realization record
    deterministic absence-search specification + frozen result
    exact successor/retirement evidence

The verifier confirms query mechanics and exact frozen bytes.

It does not replace the semantic author's interpretation of whether matched evidence is substantively sufficient.

A malformed or mechanically unresolvable evidence request rejects the current attempt before freeze.

It does not authorize task-owner editing.

    material-gap witnesses >= 6

If either floor fails:

    no extra item is selectively rerun to reach the floor
    no canonical Key A commitment is produced
    the phase stops with governed LEGACY evidence insufficiency

The two frozen negative-control source roles remain hidden from every P6 semantic session.

Their identities are used only by bounded mechanical validation.

## 9. P6C: within-source grouping

P6C is a third fresh semantic pass.

It receives only the current source's frozen unique grouping catalog and common grouping instructions.

It does not receive:

    P5 classification artifacts
    attention mappings
    P6A candidate_gap values
    P6B evidence statuses or refs
    material truth
    negative-control source role
    prior source grouping artifacts
    another key

This preserves the stronger P4 grouping precedent.

The P6C author records only:

    must_join_pairs
    must_split_pairs

The frozen realization-boundary rule remains unchanged.

For every stored pair:

    endpoints are in the same packet_source_id
    item_id_a < item_id_b
    endpoints are distinct
    pair is unique
    pair appears in only one relation
    reason is non-empty and pair-specific
    the exact pair is individually reconsidered and confirmed

Candidate generation may be non-quadratic and may use current-source semantic features.

Candidate generation never automatically creates a stored pair.

Unreviewed or uncertain pairs remain UNCONSTRAINED.

No cross-source pair is stored.

No pair padding is permitted.

The task owner mechanically verifies, without exposing labels to the semantic author, that every grouping endpoint maps to frozen P5:

    realization_required = true

No grouping outcome may revise P5 classification or P6A/P6B work.

## 10. Deterministic source lifecycle

P6A, P6B and P6C each use the same frozen 17-source order.

Semantic jobs are source-scoped.

For P6A and P6B, a source may be split into deterministic eligible-item chunks when needed for context safety.

Chunking depends only on the frozen eligible-item set and a fixed maximum, never on semantic outcomes.

P6C remains whole-source because grouping scope is within-source and pair reasoning may require any two items in the source.

A source with no eligible P6A/P6B items may be mechanically frozen as an empty semantic workload without launching a model.

Parallel semantic workers are prohibited.

Every semantic job is fresh and sequential.

## 11. Headless fresh-session automation

The owner should not be used as a clipboard transport or batch scheduler.

P6 therefore replaces the P5 manual launch/paste loop with a qualified headless local runner.

For every semantic job the runner must start a new Claude Code process.

It must never use:

    --continue
    --resume
    --fork-session from another semantic job

The runner prospectively binds:

    model
        claude-opus-5-5

    effort
        high

    interaction
        claude --print

    output
        structured JSON receipt

    session ID
        fresh runner-generated UUID

    safe mode
        enabled

    restricted filesystem mode
        enabled

    Chrome
        disabled

    MCP
        none / strict

    subagents
        prohibited

    network/web
        prohibited

P6A and P6C need only bounded file read/write/edit capability.

P6B additionally needs bounded read/search capability over the fixed read-only evidence snapshot.

Shell, PowerShell, Python, arbitrary Git commands and arbitrary process execution are not semantic-author tools.

The evidence snapshot itself provides the frozen repository bytes, so semantic evidence inspection does not require live Git.

## 12. Automated postflight and stop-on-exception behavior

The runner may automatically advance from one semantic job to the next only after a purpose-specific verifier accepts the current artifact and transcript.

Mechanical postflight includes:

    exact model
    exact effort
    fresh unique session ID
    exact private cwd
    no continue/resume
    no compaction
    exact tool allowlist
    no MCP/web/network/Agent
    exact source packet only
    exact evidence snapshot only when P6B
    exact output schema
    exact expected item IDs
    no duplicate IDs
    no forbidden fields
    artifact write discipline
    append-only phase precedent/errata logs
    no prior source artifact reads
    no later source exposure
    no classification-label mutation
    no candidate-gap mutation during P6B
    no candidate-gap/evidence exposure during P6C

Automatic retry-to-green is prohibited.

On any semantic HOLD, process failure, verifier failure, compaction, source-boundary breach, tool-boundary breach or artifact failure:

    stop orchestration
    preserve the failed attempt
    return a bounded exception receipt to the task owner
    require governed disposition before a fresh replacement attempt

A replacement attempt is always a new Claude Code process.

## 13. Phase-specific precedent isolation

    P6B evidence precedents
    P6C grouping precedents

No P6A item outcome may enter P6B precedents.

The existing global errata mechanism remains governed.

## 14. Public bookkeeping is phase-level, not clipboard-level

P5 demonstrated that one public Git checkpoint per semantic batch creates unnecessary deterministic bookkeeping cost.

P6 changes this operational layer without weakening semantic evidence.

During an uninterrupted automated run:

    private PROGRESS state
        is the authoritative fine-grained execution ledger

    private transcripts/artifacts
        retain exact per-job evidence

    public repository
        records phase design, authorization, qualified runner release,
        phase completion, and any governed exception requiring owner action

A public commit is not required after every automatically accepted source job.

If ChatGPT, the runner, or the host restarts mid-phase, execution resumes only from private accepted-progress state after a bounded reconciliation check.

No accepted job is repeated merely because the chat restarted.
