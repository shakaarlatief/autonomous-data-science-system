## 2. Proposed Amendment A1: cross-plane resolution

After identifying product/project responsibility, any genuine cross-plane artifact is resolved in this order:

    SPLIT
        preferred when distinct product/project responsibilities can be
        represented separately

    ASYMMETRIC OWNER
        when one plane defines the contract and the other only consumes it

    NAMED ROOT INTEGRATION CONTRACT
        only when both earlier outcomes fail and the artifact is genuinely
        a repository-wide contract or orchestration concern

Any artifact that reaches the final outcome without being a true contract/orchestration concern becomes recorded evidence against the Level-1 boundary rather than being silently placed.

## 3. Proposed Amendment A2: true-root responsibility and boundedness

Legitimate true-root responsibilities are limited to:

    repository-host integration
    external-tool-required anchors/configuration
    repository/workspace orchestration
    cold-start project entry
    named A1 cross-plane integration contracts

Cold-start entry includes:

    one human-readable repository entry point
    one stable machine-readable anchor to current project authority/routing

Every root member must have an explicit justification.

Before R6 constructs the target root inventory, it must preregister an expected inventory bound. Crossing that bound triggers architecture review.

## 4. Placement-order correction

Prospective placement reasoning becomes:

    Q1   Does repository host/bootstrap/tooling force true-root placement?

    Q1b  Is the artifact historical/inactive rather than part of active
         architecture?

    Q2   Is its primary responsibility product?

    Q3   Is its primary responsibility project development/governance/
         research/validation/reconstruction/preservation?

    Q3b  If genuinely cross-plane, apply A1.

    Q4   Inside the resolved plane, is there an independently justified
         workspace owner?

    Q5   Is it genuinely cross-workspace within that plane?

Historical lifecycle is therefore resolved before active ownership.

## 5. Ownership tiebreaker

> ownership follows the entity whose specified behavior or authority contract the artifact belongs to.

    deployment definitions
    provider integrations
    observability
    security
    shared contracts
