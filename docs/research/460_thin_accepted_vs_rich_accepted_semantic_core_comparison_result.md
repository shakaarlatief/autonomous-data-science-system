## 1. The owner's idea is valid

The comparison confirms an important correction to how the R2 failure should be interpreted.

R2 showed that:

    later independent semantic reconstruction
    -> authoritative rich semantics

was not sufficiently determined under the tested contract.

It did **not** establish that:

    model drafts rich semantics
    -> owner compares them with source meaning
    -> owner accepts/amends them
    -> accepted rich structure becomes authority

is invalid.

Therefore:

    OWNER_ACCEPTANCE_RESCUES_AUTHORITY_OBJECTION=true

The earlier rich family is not rejected merely because two independent semantic authors disagreed.

## 2. But rescuing authority does not automatically rescue the full rich schema

Research 459 separated authority legitimacy from representation necessity.

The 37 admitted SP-1 competency questions were replayed against both candidates.

Observed:

    admitted competency questions       37
    THIN_ACCEPTED answerable             37
    RICH_ACCEPTED answerable             37

This means the rich design can work if owner-accepted, but current machine requirements do not demonstrate that the **full richer semantic core is needed**.

## 3. Why all 37 remain answerable under THIN_ACCEPTED

SP-1 already divided Project-machine questions among:

    accepted governing consequences
        -> typed accepted clauses

    runtime/control decisions
        -> EventInterpretation
           ControlObligationSet
           RouteDecision
           AuthorityReceipt
           ActionContract
           continuity / Git / recovery contracts

    natural-owner assurance/realization facts
        -> WARRANT-F
           realizer coverage
           executable predicates
           evidence / qualification / activation facts

THIN_ACCEPTED is therefore not "store almost nothing."

It stores the cross-domain machine consequence where that consequence needs an accepted identity, while allowing specialized domains to own specialized facts.

RICH_ACCEPTED can represent many of the same facts, but current evidence does not show that duplicating them inside a universal rich obligation object adds required control power.

## 4. Rich-component audit

Thirteen functional components were audited.

### Shared core that survives either design

    stable semantic identity
    exact source/revision anchor
    governed deferral where applicable

These are not evidence for the full rich model because THIN_ACCEPTED already needs them.

### Useful but selective facts

    responsible semantic owner
    activation/effective boundary

These are useful when a consequence actually needs them.

THIN_ACCEPTED already supports them as clause slots, lifecycle facts or natural-owner references.

They do not need to be mandatory fields on every rich semantic unit.

### Facts naturally owned later

    realization boundary
    expected evidence path
    realization relation refs
    evidence refs
    qualification refs
    activation refs

These are usually J2 natural-owner facts.

Making them mandatory J1 owner judgments creates a timing problem:

    the governing author may not yet know
    how implementation will realize the requirement.

Allowing the fields to arrive later solves that problem, but then the design is adopting the same J1/J2 separation already present in THIN_ACCEPTED.

### Generic fields without demonstrated unique value

    generic materiality
    generic normative classification beyond typed consequence form

No admitted competency question currently requires a universal material boolean.

Where consequence kind matters, typed forms such as REQUIRE, PROHIBIT, GATE, AUTHORIZE, DEFER, LIFECYCLE and SEQUENCE carry more operationally specific meaning.

### Canonical unit grouping

The earlier ObligationUnit rule groups accepted propositions that share one realization boundary and evidence path.

Owner acceptance can make a chosen grouping authoritative as a decision.

It does not make the grouping a naturally stable fact when:

    realization is not known yet;
    one requirement is realized by multiple artifacts;
    one artifact realizes multiple requirements;
    implementation changes without governing meaning changing.

The representation is therefore vulnerable to forcing a birth-time partition over a relationship that is naturally many-to-many.

THIN_ACCEPTED avoids that by using clause-to-realizer coverage at J2.

### Global realization state

The earlier family used:

    UNLINKED
    LINKED
    EVIDENCED
    QUALIFIED
    OPERATIONAL
    DEFERRED

Those labels can be useful orientation views.

But the authoritative facts are the underlying realization/evidence/qualification/activation/deferral facts.

A global state is therefore safer as:

    generated view

rather than:

    separately authored governing truth.

## 5. Structural burden

The earlier functional rich annotation schema requires, per unit:

    unit_id
    source_anchor
    propositions
    responsible_semantic_owner
    realization_boundary
    expected_evidence_path
    activation_boundary
    realization_facts

with realization facts containing:

    realization_relation_refs
    deferral_refs
    evidence_refs
    qualification_refs
    activation_refs

plus the semantic operation of deciding which propositions belong in one unit.

This is not automatically excessive.

But it creates a broader mandatory review and maintenance surface.

THIN_ACCEPTED instead applies a selective admission rule:

    create an accepted cross-domain machine clause only
    when a named machine competency question needs it
    and the detail is not already owned by a bounded domain contract.

Later realization and operational facts are added by their natural owners.

The key comparison result is therefore structural:

> If RICH_ACCEPTED makes all earlier fields mandatory at governing birth, it asks J1 to decide facts that often belong to J2/J3.

> If RICH_ACCEPTED makes those fields selective, deferred or generated, it progressively converges toward THIN_ACCEPTED.

## 6. Control-power result

No current control capability was found that requires the full rich unit model.

Both can support:

    exact accepted consequence identity
    ActionContract generation
    admission/refusal/review
    realization-gap detection
    lifecycle/effective boundaries
    reconstruction
    requirement-to-realizer lineage
    recovery/control routing

provided RICH_ACCEPTED is embedded in the same broader Project-system domains.

The full rich core therefore does not currently demonstrate additional control power over the thin J1/J2/J3 allocation.

## 8. Strongest successor direction after this comparison

The strongest current direction is not "throw away rich semantics."

It is:

    thin accepted governing core
    + natural-owner domain contracts
    + J2 realization coverage
    + J3 executable predicates
    + generated richer orientation/state views
    + optional accepted rich metadata where a real competency question justifies it
    + independent detective safety net

This keeps the ability to become richer without requiring richness everywhere.

A future competency question may justify promoting a currently optional rich field into the accepted core.

## 9. Important limitation

The 37 competency questions are themselves a development inventory built from the current Project-system evidence.

They may not exhaust future needs.

Therefore:

    rich-only unique value = 0

means:

    no unique value demonstrated under the current admitted question set

not:

    no possible future value.

This is exactly why the architecture should remain extensible.
