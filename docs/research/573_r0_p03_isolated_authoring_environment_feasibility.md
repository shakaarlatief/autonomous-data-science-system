## Required boundary, without unnecessary guest restrictions

The relevant threat is reference contamination and inappropriate prior context. A guest can legitimately read its OS/toolchain, create files anywhere on its disposable disk and run local tests. There is no scientific need to reproduce a deny-every-parent-path policy **inside a guest that contains no hidden answers**. Guest-owned Git for its own construction may be legitimate; importing ADS Git history or old answer fixtures is not. Protecting host files from a guest and restricting experimental inputs available to the model remain different obligations.

For a future owner-designated instance:

- **Inputs:** materialize only the prospectively approved source world and equal common substrate, with explicit manifests/hashes. No whole ADS checkout, Git history, old reference fixtures, current exposed chat, reviewer transcript, owner key, private repo or cloud-sync profile. The historical 65-source reviewer capsule is not automatically the future primary 60/20 arm world. No actual source/task packet is selected here.
- **Host channels:** no host drives/home/credentials/SMB mounts, hypervisor or Docker socket, guest-agent channel with broad host access, shared clipboard, drag/drop, redirected printers/devices or inherited login profile. A read-only shared folder still leaks everything it contains. A narrow input image/disk or dedicated sanitized transfer directory needs its own inventory and escape checks. A different guest account name is insufficient if host accounts/storage are shared.
- **Network/model:** first synthetic local-computation preflight offline. Offline execution does not prove provider connectivity. Later authorize a fresh unresumed model session, minimum provider credentials and controlled service access; exclude host/LAN, arbitrary web/repository retrieval, external connectors/MCP and old-reference access. Enforce any required egress restriction outside the author's ability to remove it; guest-local firewall settings are not immutable if the author controls the guest. No provider, paid deployment or authentication route selected here.
- **Outputs:** owner/coordinator exports only this arm's declared files and receipts, preferably after stopping the author/guest. Do not expose a general writable host directory or re-import another arm's outputs. If a narrow output share is chosen, it starts empty per run and requires link/path and host-write negative tests. Guest output must not be automatically executed on the host. Retain hashes, execution logs and controlled provenance; no gold is needed in the authoring guest.
- **Reset/parity:** preserve one clean baseline with pinned OS/tools/dependencies/configuration. Restore/clone it before every arm; supply the same approved input/substrate version and equal budget, with fresh model/session state and no previous arm metadata, caches or outputs. Record permitted nondeterminism separately; equivalent initial conditions do not mean every log/clock/session byte must be identical. A snapshot does not erase provider-side memory or outside-guest shared state.

Windows Sandbox's [configuration documentation](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file) makes networking and clipboard enabled by default and exposes mapped-folder controls. Its disposable reset is useful, but default launch is not source-world confinement. A VM's enhanced-session/clipboard/folder integrations need analogous explicit inspection. These are conditional controls for an available environment, not instructions to create one now.
