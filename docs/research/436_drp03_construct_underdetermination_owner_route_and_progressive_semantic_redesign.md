## 5. Progressive qualification principle

The next semantic architecture should use progressive evidence where useful.

A generic progression is:

    concept / mechanism analysis
        ->
    micro real probe
        ->
    small realistic end-to-end development pilot
        ->
    focused redesign
        ->
    optional medium scale / fatigue / orchestration stress test
        ->
    final architecture + protocol freeze
        ->
    untouched confirmatory qualification

This is a principle, not a fixed mandatory sequence. A candidate may skip a stage when the stage would not change any decision, or may require a different focused probe.

Exact sample sizes are deliberately not frozen here. They must be justified by the question being tested. A small probe should contain difficult, discriminating cases rather than a large number of easy cases.

Early failure is useful. If a foundational idea fails on a small realistic probe, the default response is to learn before scaling, not to complete a large run for its own sake.

## 6. Development and confirmation are different evidence regimes

### Development evidence

During development it is legitimate to:

    inspect individual disagreements
    use examples and counterexamples
    clarify definitions
    change prompts/instructions
    change the ontology
    change the LLM role
    compare alternative representations
    change grouping or remove grouping
    prototype deterministic derivations
    run repeated small probes when each has a declared learning purpose

Development evidence exists to improve or reject candidate designs.

### Confirmatory evidence

A later confirmatory test must use:

    a frozen candidate architecture
    a frozen measurement protocol
    fixed decision gates
    untouched confirmatory evidence
    independence controls appropriate to the claim being tested
    no tuning from the observed confirmatory result

Any item/corpus used to tune a candidate becomes development evidence for that candidate family and cannot later be presented as untouched confirmation of the tuned design.

## 8. Key successor questions

The redesign must not begin with "how do we improve agreement on the current fields?"

It begins with system-level questions including:

1. Does the Project system need a canonical obligation unit at all?
2. If normative semantics are needed, should they be one mutually exclusive kind or multiple orthogonal dimensions?
3. Should grouping be inferred, explicitly authored, represented as typed relations, or eliminated?
4. Which semantics should be born explicitly at proposal/decision time rather than reconstructed later?
5. Which realization/state facts can be made deterministic once explicit source facts exist?
6. What should an LLM decide, if anything?
7. If LLM judgment remains, is the intended property zero-context reproducibility, qualified/calibrated reproducibility, bounded residual interpretation, or another contract?
8. Would examples, counterexamples, boundary cases, or a qualification curriculum improve a legitimate operational author role, or would they merely teach around a defective ontology?
9. Can a smaller semantic core support AO while leaving richer interpretation advisory/non-authoritative?
10. Is the present semantic responsibility allocated to the right Project-system layer?
11. Which parts of the current construct have independent empirical support and which are only inherited design assumptions?
12. What candidate minimizes semantic discretion while still supporting the operational decisions AO actually needs?

## 10. Scaling rule

A larger experiment is justified only when at least one of these is true:

    the smaller scale passed the properties it was designed to challenge
    the larger scale tests a new property such as fatigue, prevalence, rare cases or operational burden
    sample-size uncertainty prevents the decision at the smaller scale
    end-to-end integration introduces a risk that isolated probes cannot measure

"More data is more rigorous" is not sufficient by itself.

## 11. Anti-overfitting rule

Progressive development must not become retry-to-green.

For every development probe, record before execution:

    question
    candidate version
    corpus/fixture role
    decision-relevant outputs
    what may change after the result
    what evidence becomes development-only
    what would cause abandonment rather than another tweak

Repeated changes are legitimate during development because development is for learning. They become scientifically invalid only when tuned evidence is later misrepresented as independent confirmation.
