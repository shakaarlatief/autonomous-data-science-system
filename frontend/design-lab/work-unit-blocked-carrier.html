ADS Cockpit Design Lab · Slice 02I · BLOCKED Carrier Convergence

Can BLOCKED reuse the accepted live-status carrier language while blocker cause, blocked effect and failed execution remain semantically distinct?

The visual slot is shared, not the ontology. A work unit that cannot proceed can use the same compact dot/ring or explicit soft-shade tag language as live runtime. The underlying model still distinguishes a blocker cause, a blocked progress constraint and a failed execution attempt.

Held distinction blocker = cause · BLOCKED = constraint · FAIL = execution attempt A shared visual carrier does not require these concepts to become one semantic axis.
Refined product hypothesis

One operational-status slot can present either a live runtime state or a blocking constraint

When a work unit is blocked, it normally has no live runtime episode, so the same bottom-right status slot can communicate BLOCKED instead. If an execution merely fails but the work can still be retried, the slot communicates FAIL. If that failure creates an unresolved constraint, the current presentation may move to BLOCKED while the failed attempt remains in history/provenance.

Controlled semantic contrast

BLOCKED and FAIL can share a red family without becoming the same state

The dot carrier gives BLOCKED the sharper constraint ring while FAIL uses the smoother circular operational ring. The tag carrier uses the same accepted soft-shade motion but explicit text removes ambiguity.

Cause / effect coexistence check

Can the Cockpit show what is blocked, why it is blocked, and still distinguish runtime failure?

The Question / Blocker work unit is the visible cause-resolution work. Its red BLOCKS relationships point to affected work units. Those targets carry BLOCKED as their current constraint. A separate Model Work box carries FAIL because its current execution attempt failed but is not presently blocked.
