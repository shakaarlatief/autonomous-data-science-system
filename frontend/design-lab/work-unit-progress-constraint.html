How should a work unit show that it cannot proceed without turning BLOCKED into another disposition or runtime state?

The runtime slice is now held as conditional and switchable. This next browser isolates a different question: whether BLOCKED belongs to an orthogonal progress-constraint axis, and how that constraint can remain visually distinct from category, project disposition and runtime.

Semantic correction under test

Blocked describes inability to proceed, not where the work sits in the project lifecycle

A Current or Next work unit can plausibly be Blocked. A live runtime episode can be Waiting without the work unit being Blocked. Conversely, a Blocked work unit may have no live runtime episode at all. The visual experiment below keeps those concepts separate.
