# Independent information-need origination

**Role:** A fresh, independent contributor identifying potential information needs about the Autonomous Data Science System. This is **not** an answer-writing or experimental scoring task.

## Before starting

Describe your actual available tools, source access, connected apps, memory/other-conversation availability and any previous involvement with this project's comparisons, question sets, reference answers or solutions. If you have relevant prior exposure or can read material beyond the supplied input, disclose it and stop rather than claiming independent origination.

Read **only** the accompanying neutral orientation. Do not use websites, repositories, linked apps, prior chats, project memory or hidden/reference material. The orientation is historically scoped and incomplete; do not infer deployed or currently accepted status from it.

## What to produce

Identify up to **twelve distinct, realistic information needs** that a genuine contributor to ADS might raise. Attempt three independent needs in each of these four areas:

1. **Orientation and situation reconstruction:** Understand the project's state, responsibilities and progress as of an explicitly requested time.
2. **Project/Product relationships:** Discover a real relationship between developing/governing ADS and its application code or interface. The two sides must matter to the need.
3. **Impact and evolution:** Understand consequences, dependencies and changes across project revisions, including limits of a change.
4. **Exact evidence, authority and recovery:** Determine the evidential or authoritative basis of a claim or what would be necessary to reconstruct a bounded situation.

For each proposed need, state only:
- A natural, standalone request from a plausible project contributor.
- Its intended historical time scope (or an explicit open time-scope question).
- Why the requested information would matter to that contributor.
- Whether it is meaningfully distinct from the other proposed needs.
- Any obvious uncertainty about the existence of enough evidence, marked **NOT_YET_ADJUDICATED**.

**Do not** supply answers, expected facts, source paths, citation lists, relevance labels, suggested technologies, navigation strategies, retrieval queries, implementation steps or scoring results. Do not turn the four categories into four variations of the same request. Do not invent specific module names, approvals or events not present in the orientation. You may state that a category lacks credible needs rather than fabricate three.

The requests are **prospective candidates**, not a frozen twelve-task experiment. No candidate is accepted without a separately independent review of origin, distinctness, time scope, exact evidence and answerability.

## Outputs and separation

Create one **owner-private** Markdown file named `NEED_PROPOSALS_RESTRICTED.md` with the candidate requests and the short fields above. Treat its full wording as protected future experiment preparation. Do not paste its contents into any public/coordinating chat or repository.

Create a separate **source-free completion receipt**, `NEED_ORIGINATION_SAFE_RECEIPT.md`, with the input archive size/hash, the number of proposals per category, the number of unfilled slots, actual exposure/tool limitations and the two output filenames, byte sizes and SHA-256 hashes. Include no individual requests, source-specific hints or putative answers.

Do not create a reference key, source-admission list, exact build corpus, architecture comparison or scored evaluation. If you cannot create the protected output, report the limitation rather than expose the proposals in chat.
